## 1단계: DB & ORM

목적: 메일 한 건이 “수신됐는지, AI로 처리됐는지, 실패했는지”를 저장할 수 있게 스키마를 만든다.

1. Enum 정의

AiStatus(PENDING, PROCESSING, SUCCESS, FAILED), MailReceiveStatus(RECEIVED, REJECTED)를 domain/models/enums/ 쪽에 만든다.

코드에서는 이 Enum만 쓰고, DB에는 .value(문자열)로 저장한다.

1. 마이그레이션(027)

mail_items에 컬럼 추가:

ai_status, status, spam_score, processed_at, retry_count, last_failed_at, ai_result_raw

그리고 (ai_status, processed_at) 복합 인덱스 추가.

기존 행은 ai_status=NULL 또는 SUCCESS로 backfill.

1. ORM 수정

MailItem 모델에 위 컬럼을 넣고, 읽고 쓸 때 Enum을 사용하도록 맞춘다.

1. 상태 전이 정리

“수신 성공 → RECEIVED + PENDING”, “수신 실패 → REJECTED + ai_status NULL”, “워커: PENDING → PROCESSING → SUCCESS/FAILED” 같은 규칙을 docstring이나 constants에 한 번 적어 둔다.

여기까지 하면: “어떤 메일이 대기 중인지, 처리 중인지, 완료/실패인지”를 DB에 남길 수 있다.

## 2단계: 수신 계층 (Store-then-Process)

목적: 메일이 들어오면 저장만 하고, 스팸 판정·AI는 호출하지 않는다. Mailgun은 form으로 오니까 그걸 우리 형식으로만 바꾼다.

1. 정규화 스키마

domain/hub/mail/schemas.py에 NormalizedInboundMail(to_email, from_display, subject, body, message_id, received_at 등)을 정의한다.

“공급자 상관없이 우리가 쓰는 수신 메일 1건” 형태.

1. 공급자 추상화

providers/base.py에 verify / parse(또는 parse_and_verify) 인터페이스를 둔다.

1. Mailgun 어댑터

providers/mailgun.py에서 multipart/form-data를 받아서 HMAC 검증하고, NormalizedInboundMail로 변환한다.

config에 Mailgun Webhook Signing Key(환경 변수) 추가.

1. mail 패키지 init

domain/hub/mail/__init__.py, providers/__init__.py에서 위 모듈들을 노출한다.

1. Repository 확장

- create: ai_status, status, spam_score 등 새 컬럼 인자 추가.

수신 성공 → RECEIVED + PENDING, 실패 → REJECTED + ai_status NULL.

- update: ai_status, spam_score, folder, processed_at, retry_count, last_failed_at, ai_result_raw 등 갱신 가능하게.

- _row_to_dict: API 응답에 aiStatus, status, spamScore 등 포함.

- list_pending_for_worker:

status=RECEIVED 이고 ai_status=PENDING인 행을 SELECT ... FOR UPDATE SKIP LOCKED로 limit 건 조회.

1. 수신 API 전환

- 수신 경로에서 스팸 판정(run_spam_detection) 제거.

- 멱등: external_id(Message-Id)가 이미 있으면 200 OK 반환.

- Resolver 성공 → RECEIVED, PENDING, inbox로 저장 후 201.

- Resolver 실패 → REJECTED, ai_status NULL로 저장 후 200 (정책에 따라 owner_employee_id nullable 또는 placeholder).

- Mailgun 전용: POST /api/mail/receive/webhook/mailgun 추가하고, body는 Form으로 받아서 Mailgun 어댑터에 넘긴 뒤 같은 저장 로직 호출.

- 기존 POST /api/mail/receive(JSON)는 테스트용으로만 두고, 위 규칙(멱등·REJECTED 시 ai_status NULL)만 동일하게 적용.

여기까지 하면: 메일이 들어오면 DB에만 쌓이고, Mailgun이 재전송해도 200으로 멱등하게 처리된다.

## 3단계: 워커

목적: “PENDING인 메일을 한 건씩 가져와서 스팸 판정하고, inbox면 성과/역량 분류까지 연쇄 실행”하는 프로세스를 만든다.

1. workers 패키지

app/workers/__init__.py 만든다.

1. mail_pending 워커

- 조회: list_pending_for_worker(FOR UPDATE SKIP LOCKED)로 PENDING 1건(또는 N건) 가져온다.

- PROCESSING으로 변경: 해당 행 ai_status=PROCESSING, 필요하면 processed_at 등 설정.

- 3단계용 더미: 당장은 “무조건 정상 메일”로 두고 SUCCESS로 끝낸다.

- 4단계에서: 이 더미 자리를 classify_spam 호출로 바꾸고, 결과로 spam_score, folder, SUCCESS/FAILED 처리.

- 성과/역량: 스팸이 아니면(folder=inbox) 같은 워커 흐름 안에서 run_email_classify_and_record 호출(연쇄).

- 예외/타임아웃 시: 해당 행 FAILED, retry_count 증가, last_failed_at, ai_result_raw 저장.

실행: python -m workers.mail_pending (또는 프로젝트에서 쓰는 실행 방식).

여기까지 하면: 수신과 처리만 분리된 “비동기 파이프라인”이 돌아간다.

---

## 4단계: LLaMA 연동

목적: 워커의 더미를 실제 스팸 분류로 바꾸고, 실패 시 운영에 쓸 수 있게 기록한다.

1. 워커에서 더미 제거

classify_spam(기존 경로) 호출, 타임아웃 설정.

성공 → spam_score, folder(inbox/spam) 반영 후 SUCCESS.

실패 시 반드시:

ai_status=FAILED, retry_count += 1, last_failed_at, ai_result_raw에 에러 메시지 저장.

1. (선택) 재시도

FAILED 건을 수동 재처리 API로 PENDING으로 되돌리거나, 나중에 자동 재시도 로직 추가.

여기까지 하면: “실제 운영에 가까운” AI 메일 처리 파이프라인이 완성된다.

## 5단계: 프론트(UX)

목적: 사용자가 “어떤 메일이 분석 중인지, 완료/실패인지”를 보고, 받은편지함/스팸함 구분을 명확히 본다.

1. API 응답

목록/단건에 aiStatus, spamScore, status 등이 이미 나가도록 repository 쪽 확인.

1. 타입·매핑

프론트 MailApiItem / MailItem에 aiStatus 등 추가하고, apiMailToMailItem에서 매핑.

1. 목록 표시

- inbox vs spam: folder 값으로만 구분(아이콘·배지).

- 분석 상태: aiStatus로만 표시 (PENDING/PROCESSING → 로딩/시계, SUCCESS → 체크, FAILED → 경고).

1. 폴링

받은편지함/스팸함 화면일 때만 3~5초마다 목록 다시 불러오기.

1. 스팸 테스트

“전송됨, 분석 중” 안내 + 폴링/새로고침으로 결과 확인하도록 문구 정리.
